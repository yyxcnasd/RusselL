## 第三次审计：∃E 能否公理化？

结论：**保留为基本规则，不做成公理图式。** 理由：

- 规则形式是 `∃x A, A→B ⊢ B`，侧条件 `x 不在 B 中自由出现`。
- 若写成公理 `∃x A → (∀x(A→B) → B)`，当 `x` 在 `B` 中自由出现时该公式不成立；
  侧条件是元语言条件，无法用一阶公式图式表达。
- 在“∃ 定义为 ¬∀¬”的系统里 ∃E 可由命题演算导出；本项目把 ∃ 作为原始符号并只给
  ∃I* 公理，因此 ∃E 必须作为规则保留。

审计中还发现并修复了一个实现 bug：`src/modules.js` 的 `exists-elim` 返回
`asBody(impTree.b)`（对结构树调用 token 接口），任何实际使用都会抛
“公式必须是 token 数组”。此前没有任何关卡用到 ∃E，所以测试没有暴露。
`*94–*96` 首次用 ∃E 从配对公理推出 `∀x∀y∃u(x∈u ∧ y∈u)` 时修复为
`T.treeToBody(impTree.b)`。

## 第四次审计：∧/∨/↔ 已按定义展开 + 引理关证明（本轮完成）

结论：**∧/∨/↔/∃ 不再有派生公理模块。** 棋盘继续显示表面语法，比较与证明统一走定义展开：

| 表面写法 | 定义展开 |
| --- | --- |
| `A ∧ B` | `¬(A → ¬B)` |
| `A ∨ B` | `¬A → B` |
| `A ↔ B` | `¬((A→B) → ¬(B→A))`（即 `(A→B) ∧ (B→A)` 的展开） |
| `∃x A` | `¬∀x ¬A` |

- 唯一的定义入口是 `def-expand`（D）与 `def-contract`（D⁻）：输入输出都是 `⊢` 断言，只重写公式，不能凭空产生结论。
- 显示层（`Term.fmt / toHTML`）不做展开/收缩，因此既有公式的显示不变；`Term.eq` 一直是展开后比较，语义未变。
- 9 条派生规则本身就是可证明的引理，落在第Ⅰ章 Ⅰ-11…Ⅰ-19，参考解只用 A1–A3 + S/M + 更早引理 + D⁻；
  困难关与后续内容只以 `theorem` 引用它们，不再有“公理模块 + S”冒充派生规则的路径。
- 原来的 5 个基于派生公理的教学关（vi–x）删除，改为 D 定义 / 原始语法 / 引用已证定理 3 个符号教学关。
- 局限：`D⁻` 是“展开形 → 表面语法”的规范化折叠；同一公式可能有多种表面写法（例如 `¬A→B` 既可按 `A∨B` 折叠也可保持原始），
  折叠按固定优先级（↔ → ∧ → ∨ → ∃）取一种，显示可能与玩家手写形式不同，但 `Term.eq` 意义下等价。
